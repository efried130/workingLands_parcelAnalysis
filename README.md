## Overview

### Summary

A method and analysis to find high concentrations of working lands that border water features, as well as an accompanying parcel ranking method for identifying and contacting landowners who work them.

The pipeline measures and derives a **riparian cropland density**: acres of cropland within 100 ft of water, per square mile of a 3-mile neighbourhood. Where that density is high relative to a reference, and above an absolute floor, the cells are grouped into **zones** — contiguous blocks of concentrated riparian cropland. Every county in the state gets its zones, its rank and its row in a manifest.

The hotspot method only uses parcel data at a final, optional step. Otherwise, it only references the cropland-in-corridor geometry and the study extent. The density surface is built once for the whole state, and parcels enter only at the very end for the counties where parcel data exists.

It is designed to run on any U.S. state and digest any priority area within that state.

### Code overview

| stage | what it does | cost | runs how often |
|---|---|---|---|
| **Preprocessing** | Create `.gpkg` summarizing and clipping necessary layers to the surface of interest (geometry) | ~1 hour | once per geometry, per set of upstream settings |
| **Pass A** | one statewide corridor, lattice and neighbourhood-density surface | 1–2 hours (if cached ~10 min) | once per geometry unless cached (then skipped) |
| **Pass B** | each county's slice of that surface: its cells, zones, rank, manifest row | seconds | every run |
| **Pass C** | the parcel work — ranking, owners, contacts — for counties that have a parcel file | minutes each | only where parcel data exists |

Once Pass A `state_surface.gpkg` is on disk, changing the reference basis, the floor, a colour or a figure re-runs on the whole deliverable is trivial.

### Important input switches for run scenarios

To compare riparian cropland concentration across diverse areas, there are threshold concentrations and minimum acreages that are calculated dynamically or can be set to an absolute after examining the output. The full treatment is in Pass B; this is the short version, early, because it decides what a subset run means.

Everything below is in the same unit: **riparian-cropland acres per square mile.**

**The reference R — the relative bar.** The average riparian-cropland density of the area a cell is being compared against: `R = riparian acres in the area ÷ land acres of the area × 640`.

`BASIS` picks the area — the cell's own county, the whole state, or the cell's HUC8 region. A cell must beat `HOT_MULTIPLE × R` (1.5× by default), so R asks "is this cell dense *for where it is*?" Every county gets its own R when `BASIS = 'county'`.

**The FLOOR — the absolute bar.** A single acres-per-square-mile number for the entire run, below which no cell is hot no matter how it compares to its neighbours. It asks "is there enough here to be worth a visit at all?" It is one number, derived once, from `FLOOR_MODE` (`'knee'`, `'percentile'`, `'absolute'`, or `'off'`). Where `'knee'` is calculated within the code, `'percentile'` is calculated as an output so you can determine a minimum percentile cutoff across counties yourself, `'absolute'` is then a number you define yourself after examining the output, or `'off'` sets no minimum threshold at all and the reference is the only minimum.

**How they interplay.** A cell must clear both, so per cell they collapse into one number:

```
threshold_applied(i) = max( HOT_MULTIPLE × R(i) , FLOOR )
```

R varies by county; FLOOR does not. Whatever this one number is reported as `threshold_applied` and is written to the manifest for every county — so the number each county actually had to clear is on the record, in absolute acres per square mile, and two runs can be compared on that column.

| Code switch option | computed over | Example of a two-county run… |
|---|---|---|
| `FLOOR` (`'percentile'` or `'knee'`) | all analysed cells in the run, pooled — one number for the whole run | it is derived from those two counties only, not from the state |
| reference R, `BASIS = 'county'` | each county on its own extent | each county is judged against itself, exactly as in a statewide run |
| reference R, `BASIS = 'state'` | all analysed ground, pooled | "state average" means "average of the two counties you ran" |
| reference R, `BASIS = 'region'` | each HUC8, clipped to the analysed ground | a HUC8 mostly outside the subset falls back to the pooled average |

Again, per cell the two combine as `threshold_applied = max(HOT_MULTIPLE × R, FLOOR)`, which is written to the manifest for every county — so whatever was pooled and whatever was local, the number each county actually had to clear is on the record in absolute acres per square mile.

Three common changes, what to set, and what moves relative to the run before it. The one thing to carry through all three: the floor is one number computed across everything the run analysed, while the ratio reference depends on `BASIS` — see *Important input switches for run scenarios* above. See methods for floor and `BASIS` explanations.

#### Scenario 1 — run a new state

| set | to |
|---|---|
| `STATE_FIPS` (§0) | the new two-digit code, e.g. `'47'` |
| `PROJECT_DIR` (§1) | that state's project folder (or `FL_PROJECT_DIR`) |
| `raw_data/` | that state's CSB, NHD, cousub, HUC12, NWI downloads |

Nothing else. The state's name, postal code, county word, cache file name, download patterns and every figure title follow from `STATE_FIPS`. County names are resolved automatically (see §9).

A new Pass A — hours. The state and region references, the floor and the knee are all derived from the new state's own distribution, so a floor of 7.03 in Kentucky says nothing about what Tennessee's will be. Numbers are not comparable across states except through `threshold_applied`, which is in absolute ac/sq mi either way.

#### Scenario 2 — run a new priority area (in a new state or the same one)

| set | to |
|---|---|
| `raw_data/` | the new PA file (`*_PA_*.shp` or any `*priority*area*`) |
| `COUNTY_EXTENT_MODE` (§3) | leave `'whole_county'` — the right answer in almost every case, and the one `REPORT_WITHIN_PA` requires. Only use `'pa_only'` for a cold start where you do not want the statewide surface. |
| `REPORT_WITHIN_PA` (§3) | `True` to report inside the PA without rebuilding Pass A — the usual choice, with `COUNTY_EXTENT_MODE` left at `'whole_county'`. `False` leaves the PA as reporting columns only. |

**Changes vs. Scenario 1.** Preprocessing cuts every resource layer to the state, never to the priority area, so a new PA costs one small `pa_geo` rebuild. CSB, NHD and NWI are untouched. `'auto'` notices the source file changed and rebuilds that one layer.

Two settings control your study area, and they answer **two different questions**. Confusing them is the most expensive mistake in this pipeline, because one of them costs hours and the other costs seconds.

| Setting | Scenario | Runtimes |
|---|---|---|
| `COUNTY_EXTENT_MODE` | What ground does Pass A **measure**? | A rebuild of Pass A — hours. |
| `REPORT_WITHIN_PA` | What ground do you **report** on? | Nothing. It runs after the surface is built — seconds. |

| Situation | Set | Pass A cost | Output |
|---|---|---|---|
| You want the **statewide** product. The PA is context — you want to be able to say "of the top 20 counties, 14 are in our footprint". | `COUNTY_EXTENT_MODE = 'whole_county'`<br>`REPORT_WITHIN_PA = False` | One statewide build (hours) | Every county in the state gets a row. `pa_share` and `in_pa` say which are in the footprint. Full 3-mile measurement everywhere. |
| You want results for the **PA only** (new or old PA), and you already have a statewide surface. | `COUNTY_EXTENT_MODE = 'whole_county'`<br>`REPORT_WITHIN_PA = True` | **NONE** (minutes) | Only PA ground is reported. Every average, the floor, the zones and all figures are computed on PA ground — but each cell keeps its **full 3-mile measurement**, so cells near the boundary are still measured honestly. `band_in_report` says, per cell, how much of its 3 miles came from inside the PA. Counties overlapping the PA by less than `MIN_PA_SHARE` are dropped rather than clipped to a sliver. |
| You want PA results, you are starting a new state, and you do not want the statewide product. | `COUNTY_EXTENT_MODE = 'pa_only'`<br>`REPORT_WITHIN_PA = False` | Scales with the PA, not the state — often minutes. | A small, fast surface covering only the PA. **The trade-off:** cells near the PA boundary have their 3-mile radius truncated. Good for a first look but may need a larger surface run. |

##### How to run a new priority area if you have already run an old one

Nothing is rebuilt, for either of the first two rows above. Preprocessing cuts every resource layer to the **state**, not to the PA, so CSB, NHD and NWI are untouched; and the surface signature identifies the cache by the layers Pass A actually opens, which does not include `pa_geo`. A new boundary therefore moves nothing the surface depends on. Three steps:

1. Put the new PA file in `raw_data/` and **remove or rename the old one**. The pattern `*_PA_*.shp` will match both, and when more than one file matches, the newest wins — which is probably what you want, but the run prints which file it used and you should read that line rather than trust it.
2. Run `fl_01_preprocess.py` with `RUN_PREPROCESS = 'auto'`. It rebuilds `pa_geo` and nothing else — the log says so in one line: `pa_geo  source has changed since it was cached - rebuilding`.
3. Run `fl_02_statewide.py` with `RUN_SURFACE = 'auto'` and `REPORT_WITHIN_PA` set for the row you want. The surface loads from disk in seconds. With the mask off you get the statewide product with new `pa_share` and `in_pa` columns; with it on you get the new PA analysed on its own ground.

**Notes**

Outputs are overwritten in place. The second PA run replaces `_state/` and `counties/` from the first. If you need both side by side, copy `outputs_statewide/` somewhere else before re-running, or point `PROJECT_DIR` at a second folder.

Use the `zone_summary.csv` to filter for PA layer (toggling run PA will **recompute** all zones, thresholds, references, and floor values).

On that note, if you make Pass A measure only the PA, it **rebuilds** the surface and you will get slightly different results: a cell sitting just inside the boundary has its 3-mile radius **cut off** at the line — it is measured over less land than a cell in the middle. Otherwise, keeping the surface statewide and applying the PA afterwards avoids that entirely. Thus, a PA-only run and a statewide run are **not comparable**. The averages and the derived floor come from different ground. Every output carries a `report_mask` column to differentiate. To compare across runs use `threshold_applied`, which is in absolute acres per square mile either way.

A masked run cannot damage the surface. `state_surface.gpkg` keeps its `grid` and `rip_crop` layers — the reusable statewide surface — because those are only rewritten when Pass A actually runs. Only `grid_scored` and `zones` reflect the most recent run, so after a masked run those two layers hold PA cells while `grid` still holds the whole state. Turning the mask off and re-running restores them.

#### Scenario 3 — run a single county, or a list, within a state

| set | to |
|---|---|
| `COUNTIES` (§3) | `['047']` or `['047', '225']` |
| or, better, the environment | `FL_COUNTIES=047,225` |

To make a subset run reproduce the statewide numbers exactly, pin the threshold rather than deriving it:

```python

```

Open `fl_colab.ipynb`, set `CODE_DIR` and `PROJECT_DIR` in cell 2, run the cells. `COLAB` in §0 defaults to `'auto'` and detects Colab by itself; it mounts Drive, builds on `/content` and copies the finished folder back. **A network share or a slow project disk.** Set `SCRATCH_DIR` and the heavy writing happens on local disk, with one copy at the end. **Re-running.** Both caches check themselves, so `'auto'` is safe:

- `RUN_PREPROCESS = 'auto'` rebuilds a layer whose source file has changed, not merely one that is missing. The record is `<st>_state_layers.cache.json`.

Nor is a new priority area: what is hashed is the preprocessing manifest for the layers Pass A actually opens, and `pa_geo` is not one of them, so re-caching it leaves the signature where it was. ## Script summary

### Preprocessing — `fl_01_preprocess.py`

**Summary.** Resolves every input pattern to a file, builds the study area, cuts each national or statewide source down to the state, and writes them as layers of one GeoPackage. After this the statewide script never opens a source file again.

1. Resolve every registry pattern to a path before anything slow runs, and fail with the file's name rather than forty minutes in.
2. Print what each optional missing file costs, so a degraded run is never mistaken for a complete one.
3. Dissolve `cousub` on `COUNTYFP` into counties; union those into the state.
4. Trim the priority area to the state — it ships covering many states, and untrimmed it makes every "precise" operation below meaningless.
5. Read each resource layer with the row filter and bounding box pushed down to the driver (`STATEFIPS = '21'`, `ftype IN (460,558,336)`), which is what makes a national CSB file readable at all.
6. Clip to the state, rename the newest `CDL<year>` column to `CDL`, write the layer, and record the source's path, size and mtime in the cache manifest.
7. Check every cached layer: feature count, empty and invalid geometry, and how much of the state it covers.
8. Draw one overview figure of the cached inputs.

### Pass A — the statewide surface

**Summary.** One corridor, one lattice, one neighbourhood density, for the whole analysed extent. Tiled, checkpointed and resumable.

1. Work out each county's extent from `COUNTY_EXTENT_MODE`, and the analysed ground as the union of those extents cut to what the cache covers.
2. Split that ground into 40 km tiles, each grown by a 1-mile halo — fifty times the 100 ft buffer, so a corridor never notices the tile edge.
3. In each tile: buffer streams, wide rivers, waterbodies and wetlands by 100 ft, union them into one corridor, intersect with cropland, clip to the tile without the halo.
4. Subdivide big polygons before overlaying and use prepared-geometry fast paths for clipping.
5. Write every tile to disk as it finishes, so a machine that reboots four hours in costs one tile, not the pass.
6. Lay a 1-mile lattice over the analysed ground and sum riparian cropland acres into each cell.
7. For every cell, sum its neighbours within 3 miles — with `np.add.reduceat` on a KD-tree pair list — and divide by the land area of that neighbourhood, so a cell on the state line is not penalised for the half of its circle that is not land.
8. Save the surface plus a signature of every setting it depends on.

### Pass B — counties, references, zones

**Summary.** Attribute the one surface to counties and regions, apply the threshold rule, group hot cells into zones, and write a manifest row for every county in the state.

#### Riparian cropland density calculations

Every number below is riparian-cropland acres per square mile. For a cell `i`:

```
neighbourhood density   D(i) = sum(rip_ac over N(i)) / sum(land_ac over N(i)) * 640
                               -> column  rip_per_sqmi

own cell density        O(i) = rip_ac(i) / land_ac(i) * 640
                               -> column  own_per_sqmi

ratio                   r(i) = D(i) / R(i)
                               -> column  ratio
```

`N(i)` is every cell whose centroid lies within `BAND_MI` (3 miles) of cell `i`'s centroid, `i` included. D is a **ratio of sums**, not a mean of the neighbours' own ratios, so a half-cell on the state line does not carry the same weight as a whole one. `land_ac` is the part of the cell inside the analysed ground, which is why an edge cell is not penalised for the half of its circle that is water or another state.

#### Definition of "reference" density

The reference `R(i)` is the average riparian-cropland density of the area cell `i` is being compared against. Same units, same arithmetic as a cell's density, but over a whole area's ground instead of a neighbourhood:

```
R(area) = riparian cropland acres inside the area / land acres of the area * 640
```

`BASIS` picks which area that is, and all three are carried as columns on every cell, so the choice is a reporting decision rather than something baked into the surface:

| BASIS | the area | the question it answers |
|---|---|---|
| `'county'` | the cell's own county, on its analysed extent | where in this county should someone look? |
| `'state'` | all analysed ground — one number for everyone | which counties deserve a look at all? |
| `'region'` | the cell's HUC8 watershed | where, allowing for the fact that two ends of a state are different places? |

Two details that matter:

- **Areal, not cell-averaged.** R divides total acres by the ground, not by the cells attributed to it. A cell straddling a county line is owned by one county but holds cropland from both; averaging over cells moved a county reference by 14% on a boundary stream.
- A HUC8 with fewer than `REGION_MIN_CELLS` (30) cells or less than `REGION_MIN_COVER` (50%) of itself inside the analysed ground falls back to the state reference, and `region_ref` records which it got.

#### Three hotspot "rules"

A cell is hot when all three hold:

```
1. RELATIVE   D(i) >= HOT_MULTIPLE * R(i)        i.e.  HOT_MULTIPLE of 1.5
2. SELF       O(i) >= R(i)
3. ABSOLUTE   D(i) >= FLOOR
```

Where D is density of a neighbourhood, R is reference density of the area (area set by `BASIS`), O is the density of the cell of interest, and `FLOOR` is the minimum acres per square mile to count a cell as "hot" — set as a percentile, or found automatically by the code (where county hotspot zones drop without riparian cropland concentration rising).

Each rule guards against false positives and ensures a cell is: (1) more dense relative to the reference density; (2) its own density clears the reference, even if it merely sits next to a high concentration; (3) not the top tail of an empty county — a county with almost no riparian cropland creating hotspots out of three fields on a creek — which can be removed or set to zero.

Conditions (1) and (3) collapse into the single number the manifest reports:

```
threshold_applied(i) = max( HOT_MULTIPLE * R(i) , FLOOR )
hot(i)               = D(i) >= threshold_applied(i)  AND  O(i) >= R(i)
```

`threshold_applied` is in absolute ac/sq mi, and is therefore the column on which to compare two counties. It also explains a result that looks like a bug: when `HOT_MULTIPLE × R > FLOOR` everywhere, the floor removes nothing and the with-floor and without-floor rows of `basis_comparison.csv` come out identical. On the state basis there is one R, so that is arithmetic rather than coincidence — the floor binds only if `FLOOR > HOT_MULTIPLE × R`. `cells_cut_by_floor` and `floor_binds` say so per row.

`FLOOR` itself is set by `FLOOR_MODE`: the knee of the sweep (`'knee'`, the default, using the `'resource'` rule below), the `FLOOR_PCTL`-th percentile of D across all analysed cells (`'percentile'`), `FLOOR_AC_PER_SQMI` (`'absolute'`), or 0 (`'off'`). `BASIS = 'county'` with `FLOOR_MODE = 'off'` reduces the rule to a single county (no minimum cutoff density).

#### Determining the FLOOR — the knee

Raising the floor buys riparian concentration and costs area capture, and the knee is the floor where that trade stops paying. The run finds it four different ways and prints all four to aid in finding the right tradeoff.

- **concentration** = share of the riparian cropland designated ÷ share of the area designated. Higher is more targeted.
- **capture** = the share of the state's riparian cropland that is still inside the map. Higher is more complete.

Raising the floor increases concentrations and decreases capture.

Three of the four rules share one shape. Put gain and cost on a 0–1 scale over the swept range, and take the percentile that maximises the difference:

```
gain(p) = ( concentration(p) - min ) / ( max - min )

resource:  cost(p) = ( captured(0) - captured(p) ) / ( captured(0) - min )
counties:  cost(p) = ( counties(0) - counties(p) ) / ( counties(0) - min )

knee = the p that maximises   net(p) = gain(p) - FLOOR_KNEE_WEIGHT * cost(p)
```

Normalising both curves to 0–1 over the swept range is what makes "concentration rose 0.4×" and "nine counties dropped out" comparable quantities at all. `net` is 0 at both ends by construction, so the knee is the high point of a curve pinned at zero — the same shape as the maximum-distance-from-the-chord rule, expressed in the programme's own terms. Ties go to the lowest percentile: the floor should be the smallest cut that earns its keep. `FLOOR_KNEE_WEIGHT` tilts it — above 1 protects the cost side, below 1 chases concentration.

The fourth rule, `'curve'`, takes the parameters out. Normalise resource captured and area designated to 0–1 and take the point furthest above the chord — the classic knee, identical to maximising `captured(p) - designated(p)` in normalised units. Nothing to tune and nothing to argue about.

`'marginal'` drops normalisation entirely and works in ac/sq mi. Between two adjacent floors, the ground that leaves the map has its own density:

```
marginal(p) = ( captured_ac(p) - captured_ac(p+1) ) / ( land_ac(p) - land_ac(p+1) ) * 640

stop where  marginal(p) >= FLOOR_KNEE_MARGINAL_X * the state average
```

In words: keep raising the floor while the ground you are throwing away is *worse* than average; stop when you would start throwing away better-than-average ground. A centred rolling median (`FLOOR_KNEE_MARGINAL_SMOOTH`) is taken first, because the raw exchange rate is a ratio of two small differences and spikes wherever a step drops almost no ground.

| rule | cost of raising the floor | parameters | protects |
|---|---|---|---|
| `'resource'` | riparian cropland pushed outside the map | `FLOOR_KNEE_WEIGHT` | the resource |
| `'counties'` | counties left with no zone at all | `FLOOR_KNEE_WEIGHT` | statewide delivery |
| `'curve'` | — the geometry of the capture curve | none | nothing; it is the shape |
| `'marginal'` | the density of the ground being discarded | `FLOOR_KNEE_MARGINAL_X` | the exchange rate (default) |

> **Note:** when running initial analysis, check for agreement between the four different floor methods. A wide spread means this sweep has no single knee and the floor is a judgement call that should be made and recorded as one.

#### How sharp is each pick — the plateau

An argmax returns one number whatever the curve looks like, and these curves are flat. On the Kentucky county-basis run the `'resource'` net beat its own runner-up by 1.3% of its range and reversed direction seven times across the span it was choosing within; reporting 3.69 there implies a precision the curve does not have.

So every rule also reports its **plateau**: the contiguous run of swept floors whose net is within `FLOOR_KNEE_PLATEAU_TOL` (5%) of the rule's own net range of the best one. It changes no adopted value — the pick is still the argmax — it only says how much of the axis the rule regards as equivalent to it. `'marginal'` is a crossing rather than an argmax, so its range is the bracket between the last floor under the threshold and the first one over it, which is why it is usually the tightest of the four.

```
  HOW SHARP IS EACH PICK  (floors each rule scores within 5% of its own best)
    resource  pick   3.69   plateau   1.53 -   6.36   <- FLAT
    counties  pick   0.06   plateau   0.06 -   0.30   <- FLAT
    curve     pick   9.31   plateau   7.03 -  13.76   <- FLAT
    marginal  pick   7.03   plateau   7.03 -   7.70   the bracket the crossing falls in
    2 of 4 plateaus overlap at 7.03 - 7.70 ac/sq mi  (curve, marginal)
```

Where two rules' plateaus overlap is a far better argument for a floor than either rule's argmax, because it does not depend on which cost term you believe. The run prints the overlap, or says plainly when there is none.

Three things about the knee analysis:

1. The knees are computed on **every** run, whatever `FLOOR_MODE` says, and printed next to the floor that was actually adopted, with the ratio between it and the adopted rule's knee. Only `FLOOR_MODE = 'knee'` acts on them. So a run on a fixed percentile still tells you what each rule would have chosen.
2. They are searched on a finer grid than the table is reported on (`FLOOR_KNEE_GRID`, 2.5 percentiles): a knee at the 82nd percentile is invisible in a table that steps by five. The full curve — every rule's gain, cost and net per step — goes to `floor_knee.csv`; one row per rule, with its plateau and what it keeps, goes to `floor_knee_rules.csv`; and the adopted rule's knee is inserted into `floor_sweep.csv` flagged `knee`.
3. Figure 3b is the visual representation of the analysis: the capture curve with every rule's pick marked, then one small panel per rule showing the curve it argued from, each with its plateau shaded and printed in brackets. `KNEE_RULES_SHOWN` (§4) decides which rules are drawn.

If concentration moves by less than `FLOOR_KNEE_MIN_RANGE` across the whole sweep there is no trade-off to find, and the run says so and falls back to `FLOOR_PCTL` rather than reporting noise as a recommendation. The `'counties'` rule additionally warns when `counties_with_zones` spans only a few values, because then one county is a large fraction of the cost term and the knee jumps rather than slides.

#### The steps

1. Give each cell a county and a HUC8 region by its representative point, so a cell straddling a boundary is counted once.
2. Compute the three references as areal averages, and record which cells fell back from their region to the state.
3. Sweep the floor across ten percentiles and record what each one keeps — `hot_sqmi`, `pct_resource_hot`, `n_zones`, `counties_with_hot_cells`, `counties_with_zones`, and `concentration = pct_resource_hot / pct_area_hot` — so the chosen floor is a decision with a table behind it rather than a number. (The two county columns answer different questions: one counts counties holding a hot cell, the other counties holding a surviving zone with `MIN_ZONE_CELLS` applied.)
4. Find the knee of that sweep on a finer grid by four independent rules, report all four with their plateaus against the floor actually adopted, and adopt `FLOOR_KNEE_RULE`'s when `FLOOR_MODE = 'knee'`.
5. Apply the rule above; store `hot`, `ratio`, `reference` and `threshold_applied` on every cell.
6. Group contiguous hot cells into zones, drop any with fewer than `MIN_ZONE_CELLS` cells, and split every zone across the county lines it crosses — about half of them do. A county's share counts only if it exceeds `MIN_ZONE_COUNTY_AC` (640 ac, one whole cell), which is lattice overhang rather than a real share.
7. Measure each zone the way a biologist asks about it: riparian acres by water type, stream miles, counts of streams, rivers, waterbodies and wetlands, named waters, neighbouring zones and distance to the nearest one.
8. Record what the basis choice changes, and what the statewide neighbourhood fixed relative to a per-county run.
9. Write the manifest: status, extent basis, threshold applied, zone count and acreage, parcel availability, and `rank_by_zone_resource`.
10. Write one folder per county with its cells, zones and summary.

### Pass C — parcels, owners, contacts

**Summary.** Only for counties with a parcel file on disk. Ranks parcels by how much riparian cropland they hold and where they sit relative to the zones, then produces a contact list.

1. Find the county's parcel file by name under `raw_data/`, read it, and repair geometry.
2. Intersect parcels with the riparian cropland and with the zones; score each parcel on its own riparian acres and its place in the concentration.
3. Measure water frontage with flat end caps at a 10 m step, so edge past the end of a field is not credited, and cropland is never buffered.
4. Classify owners (individual, corporate, public, exempt) and split residency into in-county, in-state and absentee using the `cousub` town names.
5. Roll up by zone and by HUC12; write seven `zone_*.csv` breakdowns.
6. Map what is actually growing there — every overlap polygon coloured by its own CDL/NLCD class rather than by the dominant crop of the parcel it sits in, as a county map with pull-out panels and again over the parcel and HUC12 frames. See [Figures](#figures).
7. Write the full ranked table and an enriched parcel GeoPackage.

A county that fails does not stop the run: the error lands in that county's manifest row and the pass carries on.

**How to read panel B of a county sheet.** It is coloured by density ÷ the cut that ground actually had to clear (`threshold_applied`), not by density ÷ the reference. So 1.0 is the threshold on every sheet in the state, the black mark on the colour bar sits there, and the bar runs 0–2×. A context cell from the next county is drawn against its own cut, so a zone that crosses a line still looks continuous.

That matters because a ratio against a low local reference is misleading: a county whose region average is 0.6 ac/sq mi can show cells at 4× it — deep red — while holding a third of what a 7 ac/sq mi floor demands, which reads as a bug and is arithmetic. Where `HOT_MULTIPLE × reference` falls below `FLOOR`, the county is **floor-limited** and its sheet says so outright, naming both cuts and the county's densest neighbourhood. The run prints how many counties are in that position.

**How to read the two cover maps.** Every overlap polygon is coloured by **its own class**, not by the dominant crop of the parcel it sits in. Colouring a whole parcel by its most common crop paints hundreds of acres to describe a strip a few hundred feet wide, and it mislabels real ground: a grass buffer inside a corn parcel is drawn as corn, which is exactly the ground where a row-crop practice does not apply. The run prints how many parcels in that county hold more than one cover class — on Christian County it is most of them, which is the number that says whether the true-class map was worth drawing.

Classes are grouped into nine families, one flat colour each. Four carry a hue — row crop, soybeans, wheat and double-crops, grass and hay, plus teal for the NLCD-derived natural cover; the rest (fallow, developed, open water, other) are reserved neutrals, because they are context rather than crops and giving them a hue would put them in competition with the classes the map is about. The legend names the family, its acres and its share, then indents its individual classes underneath; anything under `COVER_MIN_LEGEND_AC` is pooled into one line so the legend does not run off the page.

Two details in the pull-out panels: a zone that crosses a county line has its window clipped to **this** county's share before the square is taken, so the panel shows ground a biologist here can actually visit rather than the next county's; and each panel's frame is dotted to match its box on the overview, which is the only cue that says which window it is.

`riparian_cover_true_class.csv` is the same legend as a table — same numbers, no colour required. Hand it out with the map.

|---|---|---|
| `COUNTY_NAME_FETCH` | `'auto'` · `False` | fetch the Census county list once if the cheaper sources left gaps, and cache it beside the GeoPackage |
| `COUNTY_NAME_URL` | url | where that list comes from |
| `COUNTY_NAMES` | dict | your own names — these win, and are also how you name counties on a machine with no network |

County names are resolved in this order: the `cousub` file if it carries a county-name column (most do not — TIGER's `NAME` there is the subdivision's), then CSB's `CNTY`, then a TIGER county file in `raw_data/`, then the Census list, then `COUNTY_NAMES`, then `County 047`. The run prints which sources supplied them. Nothing measured depends on a county name.

## Method Limitations

While this method supports resource targeting, it is only meant to **complement human judgment** that is bolstered by local knowledge, other social and physical resources, GIS layers, and analysis.

This method does not include the expensive **grid-origin sensitivity test** — does a zone survive moving the density lattice (1 mile grid layout)? Note that zone boundaries may not be stable and moving the initial grid overlay may alter results. A full sensitivity test can be performed for priority areas as needed.

**Parameter tuning** (i.e. different gain/cost parameters, floors, basis regions references, and concentration multipliers) is suggested before finalizing the analysis.
